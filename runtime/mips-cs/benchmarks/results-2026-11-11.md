# MIPS-C# performance results — 2026-11-11

In this run, PSP interpreter median frame work fell 20.7%, PSP JIT work was nearly flat, and desktop median frame work increased 9.0%. PSP results are from PPSSPP emulation.

This comparison starts from the safe implementation at `85efd894d3d43af69f19842306ace0ff3f789288`, freshly built and archived before the two optimization stages. It does not compare against the earlier unsafe implementation. The baseline snapshot is an external input under `artifacts/mips-cs/safe-core-before-2026-11-11`, not a repository asset; retain it to reproduce the exact comparison. Safe C# and the existing collector were retained.

## Desktop portable core

The final run's median sample p50 increased from 508.3 to 553.9 µs per frame (+9.0%), while pooled p99 fell from 2,048.0 to 1,876.1 µs (−8.4%). The p50 ranges across individual samples overlapped: 483.5–539.3 µs before and 510.7–605.2 µs after, indicating substantial sample variation. Mean measured current-thread managed allocation was 587.68 bytes per frame for both; it excludes native allocations. Median process peak working set was 32,333,824 → 32,542,720 bytes, and median private memory at completion was 12,484,608 → 12,763,136 bytes. These process-wide values include startup and warmup. All samples recorded zero CLR collections, which does not count the guest collector.

This run used 1,200 frames per sample, 500 warmup frames and five fresh-process samples per variant in alternating order. The desktop host uses a deterministic 17 ms clock. Frame timing runs from the previous `Present` exit to the next entry, excluding startup and `Present` logging; collection frames remain included. ## PSP results

The final PSP measurements ran 600 requested frames per sample, with 100 warmup frames and three samples per variant and engine, alternating before/after order. All 7,200 requested PSP frame rows matched baseline draw counts and geometry. The additional terminal frame some runs produce is excluded. Each sample uses PPSSPP emulation; these values do not establish physical PSP performance or an FPS guarantee.

| Engine | Median sample p50 before → after (µs) | Change | Pooled p99 before → after (µs) |
| --- | ---: | ---: | ---: |
| Interpreter | 57,241 → 45,420 | −20.7% | 60,857 → 49,068 |
| JIT | 4,800 → 4,768 | −0.7% | 8,329 → 8,295 |

Each PSP sample produced the same p50 within its engine and variant; this is a property of these PPSSPP runs, not evidence of physical-device stability. `-NaturalGc` was set for both variants; this safe runtime uses pressure-triggered collection. Interpreter samples each reported 25 collections and JIT samples 24, before and after.

The largest logged native array-payload totals were 1,475,754 → 1,112,974 bytes for interpreter samples and 1,475,778 → 1,112,918 bytes for JIT samples. These are sampled tracked payload totals, including metadata and backing arrays; they exclude array headers and are not process peak memory. Both revisions use the same collector. Generated JIT code shrank from 494,608 to 490,540 bytes (4,068 bytes), and EBOOT size changed from 328,042 to 327,866 bytes.

## Validation and reproduction

Validation covered 12 PSP fixtures in each of interpreter and JIT modes (24 executions total), 54 checks and 27 managed combinations, and portable plan, root and cache scenarios. A Roslyn syntax audit confirmed safe C# and braces, with no Unsafe or MemoryMarshal use in the portable source. Across both final runs all 19,200 requested frame rows matched geometry and draw counts. All 12,000 desktop frame rows also matched exact instruction and call counters. The PSP application uses a real clock for FPS text decisions, so small instruction-counter differences can occur even when geometry matches; the desktop clock is deterministic.

The host recorded Windows 10.0.26300 x64, Intel64 Family 6 Model 170 Stepping 4, .NET SDK 10.0.300 and runtime 10.0.8, with no `DOTNET_` or `COMPlus_` environment overrides. The same archived guest DLL was used in both variants (SHA-256 `F4EA41FDFA9C074C80D69F05C235A1FFD8D3D9C53247944801CB5332AA7F5EBB`). Before EBOOT SHA-256 was `34CC240CB8AE9ECFADE55290A78169BC82BE87F60775726D764991B4AE1B254A` and after EBOOT SHA-256 was `88FE81D905E1B907A67E6BECBAD714F9A4F575114CC1A84B58E10D2A6DB2808B`. PPSSPP executable SHA-256 was `27D3EDBB06DC623DAB60877D3E3A975AEF4034C7D4FAC464E92FD4998864D2EC`. Source and binary hashes for each run are in its manifest.
