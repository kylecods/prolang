# MIPS-C# benchmark results — 2026-11-08

The safe rewrite was slower in this comparison. On the measured cube workload, median sample p50 frame work increased by 23.2% on the desktop portable core, 83.7% in the PSP interpreter and 68.5% in the PSP JIT under PPSSPP. These measurements do not establish speed parity.

| Engine | Median sample p50 before → after (µs) | Change | Pooled p99 before → after (µs) | Change |
| --- | ---: | ---: | ---: | ---: |
| Desktop portable | 408.1 → 502.9 | +23.2% | 1,601.9 → 1,895.9 | +18.4% |
| PSP interpreter, PPSSPP | 31,156 → 57,230 | +83.7% | 37,005 → 60,863 | +64.5% |
| PSP JIT, PPSSPP | 2,848 → 4,800 | +68.5% | 8,240 → 8,336 | +1.2% |

The JIT's measured p50 and p99 CPU work are under 16.7 ms per frame in PPSSPP. That is not a physical PSP measurement or a guarantee of 60 FPS; rendering, scheduling, and hardware can change the result. The safe desktop samples varied: p50 ranged from 495.8 to 519.6 µs and one frame reached 7.284 ms. The baseline sample p50 range was 396.3–429.0 µs. PPSSPP timing and its repeated sample values reflect emulation, not independent physical hardware trials.

Each process requested 1,200 frames; the first 500 were warmup. Five desktop and three PSP samples per variant ran in alternating order. All 26,400 requested frame rows matched the corresponding engine's baseline draw counts and geometry, including warmup. The remaining 15,400 rows contributed to timing statistics; collection frames were retained. Percentiles select the observed value at `floor((n-1)*p)`; pooled p99 combines measured frames across samples. The same archived 22,016-byte guest DLL was used throughout. `-NaturalGc` disabled the baseline test host's forced 30-frame collections. The safe runtime ignores that flag and performs its own pressure-triggered collection: both used their normal automatic behavior, with different implementations and thresholds.

Desktop measures from the previous `Present` exit to the next entry, excluding startup and Present logging. Managed allocations averaged 0.0 bytes per measured frame before and 587.68 after; the baseline uses `NativeMemory`, which this counter omits, so those figures do not compare total allocation. Median process peak working set was 31,952,896 → 32,391,168 bytes and median private memory at completion was 12,120,064 → 12,587,008 bytes; these process-wide values include startup and warmup. All desktop samples reported zero CLR collections; this does not count guest collector activity. The PSP recorded heap maxima and collection counts in the raw process statistics, but the safe runtime's totals include metadata and backing-array payloads and exclude array headers, whereas the old collector reports guest allocations. They are not directly comparable. Generated PSP JIT code was 513,332 → 494,608 bytes; EBOOT size was 312,306 → 328,042 bytes.

The recorded host was Windows 10.0.26300 x64, Intel64 Family 6 Model 170 Stepping 4, .NET SDK 10.0.300 and runtime 10.0.8. No `DOTNET_` or `COMPlus_` variables were recorded; default tiering was used. Environment and instrumentation details are in the artifacts.
