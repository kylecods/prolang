# MIPS-C# refactor results — 2026-11-15

This run measures a structural refactor of `runtime/mips-cs/portable/` against the code it replaced. In this run the PSP interpreter's median frame work fell 11.8% (45,420 → 40,079 µs) and the PSP JIT's fell 1.0% (4,768 → 4,718 µs). The desktop median sample p50 fell 13.5%, but desktop timing on this host is so noisy that the before and after sample ranges overlap almost completely, so read it as "no regression", not as a speedup. PSP results are from PPSSPP emulation. The refactor was meant to be neutral, so the PSP interpreter figure needs the explanation in the next section: it comes from one C-side change, not from the C# restructuring.

The baseline is the safe implementation at `4eec832` (HEAD when the refactor started), freshly built and archived as `artifacts/mips-cs/safe-core-before-refactor` before any source edit. It is an external input, not a repository asset; retain it to reproduce the comparison. The refactor itself is uncommitted in the working tree. The same archived guest DLL (SHA-256 `A8093E0162E1C9926E65DB26B747849146B5627A499E6D22A07455636803D114`) ran in both variants.

## What changed

**The refactor (no intended behaviour change).** The one `static partial class VM` of about 3,800 lines became one focused `internal static class` per concern in a flat `portable/` (loader, metadata, type system, decoder, verifier, planner, natives, objects, heap, arithmetic, interpreter, MIPS assembler, register cache, JIT, runtime). The bare numbers (CIL opcodes, value kinds, element and type codes, metadata tables, MIPS opcodes, functs, registers and frame offsets, JIT helper and trap numbers, limits) became named constants, and cryptic names (`sw`, `Td`, `Mr`, `Z`, `Bad`, `nargs`) became descriptive ones. Long cold methods (`Load`, `Decode`, `Native`, `RowSize`, `Compile`, `EmitBody`) were split into named steps, and every class and non-trivial method has XML documentation covering the invariants (the overloaded `HeapObject.Parent`, `Value.Data` per kind, the plan flag layout, copy-on-write in `Objects.WriteAddress`, the register cache). The dead `MethodBody.Machine` field was removed. `README.md` gained a source map, a "Portable C# rules" section and a "C ABI contract" section. The code stays inside the subset `cs-to-c` accepts; the translator and `unsafe`-free rule are unchanged. `DesktopHost` and the `Host` API names and signatures are unchanged, and all diagnostic strings are byte-identical.

**The one C change: `pvm_at` is `always_inline`.** `psp/arrays.h` defines the checked accessor behind every translated array access. `cs-to-c` emits every method with external linkage, so GCC's unit-growth budget for inlining is spent on cold load-time code. Splitting the cold methods shifted that budget: with the refactor and no attribute, `Interpreter.ExecuteResolved` stopped inlining `pvm_at` and the PSP interpreter's median frame work came out 5.8% *slower* than the baseline. The attribute makes the hot path independent of what happens to cold code. It costs `.text` (see below) and was approved as the one change outside `portable/`'s structure.

**Why the interpreter ended up faster than the baseline.** The structural changes should not do this, so this is a hypothesis rather than a measured attribution. I checked the two ELF files: the baseline's `VM_ExecuteResolved` contains 60 out-of-line `jal pvm_at` calls (191 call sites in the whole program), and the final ELF has none. The baseline was already paying for an un-inlined accessor in its hottest function, and forcing the inline removes that cost. I did not build the baseline source with only the attribute added, so the split between the attribute and the other changes is not isolated. The JIT barely moves (−1.0%), which fits the guess that JIT-compiled methods reach the interpreter's code only through the Slow helper.

## Desktop portable core

The median sample p50 fell from 1,772.4 to 1,533.0 µs per frame (−13.5%), and the pooled p50 from 1,704.2 to 1,621.5 µs (−4.9%). Pooled p99 went 3,506.6 → 3,399.4 µs (−3.1%) and the maximum 4,583.7 → 4,253.0 µs. The p50 ranges across individual samples overlap almost completely: 1,356.7–2,137.5 µs before and 1,373.8–1,915.8 µs after, a spread of about 58% within either variant, far larger than any difference between them. The ±5% median criterion cannot be judged at this noise level; the defensible reading is that the refactor is not slower. Mean measured managed allocation was 593.94 bytes per frame for both variants (unchanged; it excludes native allocations). Median process peak working set was 27,451,392 → 27,586,560 bytes and median private memory at completion 11,411,456 → 11,464,704 bytes (both include startup and warmup). Every sample recorded zero CLR collections, which does not count the guest collector.

This run used 600 frames per sample, 100 warmup frames and five fresh-process samples per variant in alternating order. The desktop host uses a deterministic 17 ms clock. Frame timing runs from the previous `Present` exit to the next entry, excluding startup and `Present` logging; collection frames remain included. ## PSP results

The PSP measurements ran 600 requested frames per sample, with 100 warmup frames and three samples per variant and engine, alternating before/after order, with `-NaturalGc`. All 7,200 requested PSP frame rows and all 6,000 requested desktop frame rows matched the baseline's draw counts and geometry (13,200 rows in all); `compare.ps1` withholds timings on any mismatch.

| Engine | Median sample p50 before → after (µs) | Change | Pooled p99 before → after (µs) | Change |
| --- | ---: | ---: | ---: | ---: |
| Interpreter | 45,420 → 40,079 | −11.8% | 49,151 → 43,783 | −10.9% |
| JIT | 4,768 → 4,718 | −1.0% | 8,283 → 8,212 | −0.9% |

Each PSP sample produced the same p50, p99 and maximum within its engine and variant; this is a property of these PPSSPP runs, not evidence of physical-device stability. Maxima were 49,310 → 43,932 µs (interpreter) and 8,376 → 8,300 µs (JIT). `-NaturalGc` was set for both variants; the safe runtime uses pressure-triggered collection, and each sample reported 25 collections for the interpreter and 24 for the JIT, before and after.

The largest logged native array-payload totals were 1,112,974 → 1,112,366 bytes (interpreter) and 1,112,918 → 1,112,310 bytes (JIT), 608 bytes lower in both, which is the 4 bytes per method of 152 methods that the removed `MethodBody.Machine` field occupied. These are sampled tracked payload totals that exclude array headers; they are not process peak memory. ## Phase 5b trial: reverted

Phase 5b moved the largest `ExecuteResolved` case groups into private `[MethodImpl(MethodImplOptions.AggressiveInlining)]` helpers so the switch reads as dispatch: `call`/`callvirt` and delegate invocation, `newobj`, the instance-field group, the three static-field operations, and the array element load and store groups (eight helpers). The attribute is dropped by `cs-to-c` (`runtime.c` contains no trace of it) and the helpers are emitted with external linkage, so on the PSP GCC decides whether to inline them. The trial's source is kept as [`Interpreter.cs`](../../../artifacts/mips-cs/refactor-snapshots/phase-5b-trial/Interpreter.cs).

| Measure | Pre-5b | 5b trial | Change |
| --- | ---: | ---: | ---: |
| PSP interpreter cube p50 / p99 (µs, frames 2–600) | 40,071 / 43,783 | 39,274 / 42,981 | −2.0% / −1.8% |
| PSP JIT cube p50 / p99 (µs, frames 2–600) | 4,718 / 8,212 | 4,759 / 8,253 | +0.9% / +0.5% |
| ELF `.text` | 249,112 | 249,408 | +296 (+0.1%) |
| Desktop median sample p50, trial vs control (µs) | 1,435.2 (range 1,266.7–2,039.7) | 1,517.7 (range 1,302.2–2,645.8) | +5.7%, within noise |

The desktop pair ran with `-Frames 1200 -WarmupFrames 500 -DesktopSamples 5` against the same baseline, once with the pre-5b source (control) and once with the trial. The same unchanged baseline code measured 1,528.0 µs in the control run and 1,610.9 µs in the trial run, a 5% difference between two runs of identical code, which is as large as the effect being looked for. Against its own run's baseline the median sample p50 was −6.1% for the control and −5.8% for the trial. The pooled p50 ratio did move (0.98 control, 1.06 trial) but the trial's third sample was elevated for both variants (2,604.9 and 2,305.3 µs), and its fourth only for "after" (2,645.8 µs against 1,503.2 µs for the paired "before"), which accounts for most of it. [Trial](../../../artifacts/mips-cs/safe-core-bench-5b-trial/summary.json) and [control](../../../artifacts/mips-cs/safe-core-bench-5b-control/summary.json) have the full data.

The gate was PSP p50 within ±1% of 40,071 µs (interpreter) and 4,718 µs (JIT), and desktop not slower beyond noise. The JIT (+0.9%) and desktop (inconclusive but not distinguishable from the control) passed. The interpreter moved −2.0%, outside the band in the favourable direction. The strict log comparison also failed on one log: `interpreter/cube` differed in the instruction count of 60 of 600 frames, by 7 instructions each time, while every geometry hash and draw count matched and the non-strict comparison passed. That is the known dependence of the interpreter's instruction counts on its speed (the guest reads a real clock for its frame-rate text), here triggered by the faster build. Taken literally, the interpreter result fails the gate, and the 2% gain comes from the same GCC inlining sensitivity that already made one refactor 5.8% slower, which is not a property worth locking in for a readability change. **Decision: revert.** `ExecuteResolved` was restored from the phase-5b snapshot, the source is byte-identical to it, and the rebuilt ELF is byte-identical to the pre-5b ELF, which re-measured 4,718 and 40,071 µs. If 2% on the interpreter is wanted, the trial source above can be copied back, but then `refactor-baseline-v2` must be re-recorded for the strict comparison.

## Reproduction

After preparing the archived baseline as described in the [benchmark guide](README.md) and building the current runtime:

```powershell
dotnet build runtime/mips-cs/portable/Portable.csproj -c Release --nologo -v quiet
dotnet runtime/mips-cs/portable/bin/Release/net10.0/Portable.dll --self-test
./runtime/mips-cs/test.ps1
./runtime/mips-cs/golden.ps1 -Check
./runtime/mips-cs/build-psp.ps1 -Distro Ubuntu-24.04
$emu = "$PWD/artifacts/psp-tests/emulator/PPSSPPWindows64.exe"
./runtime/mips-cs/test-psp.ps1 -SkipBuild -Emulator $emu -Frames 600
./runtime/mips-cs/test-psp.ps1 -SkipBuild -Emulator $emu -Frames 600 -NoJit
./runtime/mips-cs/test-psp.ps1 -SkipBuild -Emulator $emu -Fixtures
./runtime/mips-cs/test-psp.ps1 -SkipBuild -Emulator $emu -Fixtures -NoJit
./runtime/mips-cs/compare-psp-logs.ps1 -Strict -Baseline artifacts/mips-cs/refactor-baseline-v2
& runtime/mips-cs/benchmarks/compare.ps1 -Desktop -Psp -NaturalGc -Emulator $emu `
    -BaselineDirectory "$PWD/artifacts/mips-cs/safe-core-before-refactor" `
    -OutputDirectory "$PWD/artifacts/mips-cs/safe-core-bench-refactor" `
    -Frames 600 -WarmupFrames 100 -DesktopSamples 5 -PspSamples 3
```

Give `compare.ps1` absolute directory paths: it resolves relative ones against the process's working directory, which `Set-Location` does not change in PowerShell. Leave a few seconds between `test-psp.ps1` runs, because copying the emulator over a copy that is still closing fails. To reproduce the 5b trial, copy `artifacts/mips-cs/refactor-snapshots/phase-5b-trial/Interpreter.cs` over `runtime/mips-cs/portable/Interpreter.cs`, rebuild, and run the same gates; the control is `artifacts/mips-cs/refactor-snapshots/phase-5b/portable/Interpreter.cs`.

## Caveats

- **PPSSPP is not hardware.** `work_us` is the host's measurement under emulation. These figures do not establish physical PSP frame rate or an FPS guarantee, and the interpreter's 11.8% could be larger or smaller on a real MIPS core with a real cache.
- **Desktop noise is large.** The samples of one variant spread by about 58% on this laptop, runs of identical code differ by about 5%, and the host is not the one used in earlier results. Desktop conclusions here are limited to "not slower"; a quiet host with more samples is needed to resolve differences under about 15%.
- **Instruction counts depend on emulated speed.** The cube reads a real clock (`time_millis`) for its frame-rate text, so a faster or slower build can execute a few more or fewer instructions in some frames. Geometry and draw counts never change. This is why the strict log comparison is tied to a specific recorded speed and why the 5b trial tripped it.
- **The interpreter result is not attributed.** The `pvm_at` inlining is the likely cause (see above), but no experiment isolated it, and a different GCC version or a change to cold code could move it by several percent again; that fragility is the reason the attribute exists.
- **Heap figures are payload totals,** not process peak memory, and exclude array headers.
